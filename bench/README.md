# bench

内存占用随对局数的测量与判定工具，配套仓库内 `grid/` `smooth/` `region/`。

目标只有两件事：**从监控曲线上分辨出形状**（直线 = 每局都留残留；对数/饱和 = 残留被部分回收），
**把直线斜率换算成每局的泄漏条目数**，并给出释放时机的取舍依据。

## 快速开始

```sh
make report        # 全部重跑：三档对局数、对照实验、释放时机、分析器自检
```

单项：

```sh
make run           # 真实模块 3/10/30 局各一次     -> measurements/repo.csv
make controls      # 已知真值的三种形状对照         -> measurements/controls.csv
make two-mib       # 每局 2 MiB 的对照，验证换算     -> measurements/two_mib.csv
make cache-run     # 缓存容量/空闲TTL 扫描           -> measurements/cache.csv

python3 analyze.py --csv measurements/repo.csv --module grid --entry-bytes 72
python3 analyze.py --csv measurements/x.csv --metric rss_kb   # 直接读监控列
python3 pick_release.py --csv measurements/cache.csv
python3 test_analyze.py
```

## 一、内存占用随对局数的表达式

设定：

| 符号 | 含义 |
|---|---|
| `M0` | 首局结束时的占用（基数：常驻结构、启动期分配） |
| `p` | 每局新产生、本应释放的路径条目数 |
| `s` | 每条路径条目的字节数 |
| `r` | 每局残留比例，`0 ≤ r ≤ 1`（`r=1` 表示条目永久不释放） |

三种形状：

```
完全残留      M(n) = M0 + p·s·n                       直线，斜率 = p·s
部分残留      M(n) = M0 + p·s·(1-(1-r)^n)/r           收敛到 M0 + p·s/r
按对数衰减    M(n) = M0 + b·ln(n)                     缓慢无界
```

判据落在**一阶差分**上，而不是曲线长什么样：

- 差分恒定 → 直线，`ΔM = p·s`，是真正的泄漏。
- 差分每局递减、且与剩余量成正比 → 几何/饱和，收敛到 `p·s/r`，是回收慢于产生，不是无界泄漏。
- 差分按 `1/n` 衰减 → 对数，通常来自去重/索引类结构，长期仍无界。

`analyze.py` 用四个最小二乘模型（`flat / linear / log / saturating`）按 AICc 排序，
再用**前后半程斜率**做形状复核：真曲线的后半程斜率必须明显低于前半程，且降低幅度要超过
噪声误差。只靠 AICc 在短窗口上会把"恰好后段偏平的直线"误判为饱和曲线，这一点由
`test_analyze.py` 里的带噪直线用例固定住。

### 实测：本仓库三个模块

`make run`，每局 = 模块自检完整跑一遍，同进程连续执行：

| 模块 | 3 局 | 10 局 | 30 局 | 每轮 live_bytes | 每轮 live_blocks |
|---|---|---|---|---|---|
| grid | r1=4104 | r10=4104 | r30=4104 | 常数 4104 | 常数 1 |
| smooth | 4104 | 4104 | 4104 | 常数 4104 | 常数 1 |
| region | 4104 | 4104 | 4104 | 常数 4104 | 常数 1 |

**结论：斜率 = 0，每局泄漏 0 条。** 三个模块没有任何 `malloc`，全部是栈上定长数组
（`g/f/closed/parent/open` 各 `MAXN=192` 个 int），LeakSanitizer 也报 0 泄漏。
所以"每局涨 2 MB"在这份代码上复现不出来——它要么来自监控所覆盖的更大系统，
要么来自测量方式本身（见第四节）。第 `0` 行是进程冷启动基线，`analyze.py` 一律丢弃，
不参与拟合。

`live_bytes` 里恒定的 4104 B 是 libc 在首次 `printf`/`fopen` 时分配并常驻的缓冲，
只出现在第一局之前，属于基数 `M0`，不是斜率。

## 二、从斜率反解泄漏条目数

直线的斜率就是每局的残留字节数。换算需要每条目的字节数 `s`：

```
泄漏条目数 p = 斜率 [B/局] / s [B/条]
```

`s` 有两种取法，优先用第一种：

1. **直接用条目计数**（`live_blocks` 斜率）。`allocwatch` 拦截了 `malloc` 家族，
   净存活块数就是条目数，斜率直接是 `p`，无需假设大小。
2. **用字节斜率除以 `s`**。`s` 由调用方传入（`--entry-bytes`），或者用两个斜率相除
   自动反推：`s = 字节斜率 / 块数斜率`。

### 实测：对照实验（已知真值）

`make controls` 注入三种形状，`make two-mib` 注入监控报告的量级：

| 注入真值 | 分析器判定 | 恢复的斜率 | 恢复的条目数 |
|---|---|---|---|
| 每局 40 条 × 72 B，不回收 | 直线 | 2880 B/局 | 40.0 条/局 ✓ |
| 每局 40 条，全部回收 | 无残留 | 0 | 0 ✓ |
| 每局 40 条，回收 25%（50 局） | 饱和 | 早期 +174.8 / 晚期 +0.0 B/局 | 不按泄漏计 ✓ |
| **每局 2 MiB（29127 条 × 72 B）** | **直线** | **2097144 B/局** | **29127 条/局 ✓** |

最后一行就是"每局涨两兆"的完整反推示例：2 MiB / 72 B ≈ 29127 条路径条目。
注意这是**假设**每条目 72 B 的结果；条目大小一改，条目数按 `2097152 / s` 反比变化：
`s=32 B → 65536 条/局`，`s=128 B → 16384 条/局`。
同一份数据只读监控的 RSS 列（`--metric rss_kb`）也能得到斜率，
误差约 ±0.3 KB/局，条目换算仍需 `s`。

## 三、释放时机的取舍

`cache.c` 对同一段确定性回放（每局 200 次查询，热点占比 60% / 90% 两档）扫容量与空闲 TTL，
同时记录**内存峰值**和**命中率**。`pick_release.py` 把两条曲线并成一条决策：
每放弃 1 个命中点能省多少字节。

热点 90% 时（本机实测，峰值 B / 命中率）：

| 策略 | 峰值 | 命中率 | 相对全保留：省字节 / 失命中点 |
|---|---|---|---|
| 全保留 | 895,104 | 0.302 | — |
| cap=512 | 409,608 | 0.205 | 485,496 B / 9.7 点 |
| cap=128 | 105,480 | 0.061 | 789,624 B / 24.0 点 |
| 全保留 + TTL=1 | 263,880 | 0.111 | 631,224 B / 19.1 点 |

**拐点在 cap=512**：省掉 54% 峰值，代价是命中率从 30% 降到 20%。
再往下降（cap=128）省下的边际字节换来的命中损失翻倍，不划算。

TTL 的读法更直接：基线命中率 0.302 意味着复用间隔约 `1/0.302 ≈ 3.3` 次查询，
TTL 短于这个间隔就必然错过它花钱留下的那些条目——实测 TTL=1 把命中率打到 0.111，
低于同条件下 cap=512 的 0.205。**按容量淘汰比按时间淘汰更贴合这里的复用分布。**

定释放时机的经验规则：

1. 先测命中率随容量的曲线，找边际收益开始下降的拐点（这里是 512 条）。
2. TTL 只用来兜底"长期不再访问"的冷条目；设成 `≥ 2 × 平均复用间隔`。
3. 用峰值而不是均值做约束条件——监控报警看的就是峰值。

## 四、关于"每局涨 2 MB"的前提

本仓库代码每局残留为 0（第一节）。如果监控曲线确实是每局 +2 MB 的**直线**，
按第二节，这对应每局约 29127 条 72 B 的路径条目没有被释放；若曲线是**对数/收敛**的，
则对应一个缓慢填充的上限缓存（第三节那种），需要的不是补 `free`，而是设容量上限。

两种处理完全不同，所以**先用监控数据判形状**，再决定改哪里：

```sh
# 把监控导出的 (局数, RSS) 存成 CSV，列名 round,rss_kb[,module][,run]
python3 analyze.py --csv 监控.csv --metric rss_kb
```

若输出 `linear`，用斜率除以条目大小得到泄漏条目数；
若输出 `saturating`/`log`，按第三节定容量与 TTL，而不是去找缺失的 `free`。

## 文件

| 文件 | 作用 |
|---|---|
| `allocwatch.c/.h` | 拦截 `malloc` 家族，统计净存活字节/块数；单线程 |
| `navbench.c` | 多局运行器：同进程重复跑模块自检，逐局输出 RSS 与堆计数 |
| `control.c` | 已知真值的合成负载（泄漏/回收/部分回收） |
| `cache.c` | 缓存容量与空闲 TTL 的释放时机扫描 |
| `analyze.py` | 形状判定、斜率、条目换算、10% 门槛 |
| `pick_release.py` | 由峰值+命中率曲线定位拐点 |
| `test_analyze.py` | 分析器回归测试（9 项） |

## 测量口径说明

- **RSS** 来自 `/proc/self/statm`，含分配器未归还给内核的页；对"进程还占着多少"这一问题
  是正确口径，对"其中多少是本模块造成的"会偏大。
- **live_bytes** 是 `malloc_usable_size` 的净和，排除了分配器缓存，反映的是真正未释放的对象。
- 两者一起看：RSS 涨而 live_bytes 平 → 碎片或分配器保留，不是泄漏。
- `navbench` 每档在**独立进程**中运行，避免上一档的堆影响下一档。
- 第 0 行为冷启动基线，被分析器排除；这是 `make report` 各档数字与原始 CSV 行号差 1 的原因。
